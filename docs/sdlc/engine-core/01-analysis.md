# 01 — Analysis: engine-core

- **Feature slug:** `engine-core`
- **Date:** 2026-10-25
- **Request:** Implement `src/Engine` — the pure, deterministic, framework-free rules engine — as plain PHP 8.5 with `strict_types`, readonly value objects and backed enums. Deliver an immutable `GameState` with `with*` methods and array (de)serialization, a `VariableSchema` with type validation, a validated JSON AST for conditions (13 ops) and effects (8 ops), stateless services (`ConditionEvaluator`, `EffectApplier`, `NextSceneResolver`, `Transition`), a deterministic `Rng` abstraction that nothing uses yet, a `StoryGraph` interface (plus `SceneNode` / `ChoiceNode` / `NextRule`) that `src/Content` will implement later, and four readonly event classes. Unit tests per op family plus determinism, redirect-loop, ending and exception cases, using an in-memory `StoryGraph` double. Acceptance: `make qa` green, deptrac confirming Engine has no outgoing dependency except Shared, and a coverage report showing 100% lines on `src/Engine`.

This is the first real production code in the repository. `src/Engine/` and `tests/Unit/Engine/` currently contain only `.gitkeep`; the whole of `src/` contains exactly one PHP file, `src/Kernel.php`.

## Scope

**In scope**

- Everything under `src/Engine/**`: value objects, enums, AST node classes, exceptions, the four services, the `Rng` abstraction, the `StoryGraph` / `SceneNode` / `ChoiceNode` / `NextRule` contract, `TransitionResult` / `EffectResult`, and the four event classes.
- Unit tests under `tests/Unit/Engine/**` (see OQ-1 — **not** `tests/Engine`), including an `InMemoryStoryGraph` test double that lives in `tests/`, never in `src/Engine`.
- The **serialized array shape** of `GameState`, `Condition` and `Effect`. These are produced and consumed only inside the Engine today, but they are the de-facto wire format that the YAML compiler in `src/Content` and the session persistence in `src/Play` must later target (see *Data & schema impact*).
- A written statement of the AST operator set, either as docblocks on the two enums or as a short spec document. The domain-model rule in CLAUDE.md ("adding an operator means adding it to the AST spec, the evaluator/applier, and its unit tests") presupposes an AST spec that does not exist yet; this feature either creates it or explicitly defers it (OQ-14).
- Possibly a coverage driver in the dev Docker image plus a `composer coverage` script — **only if** the user accepts OQ-2, because the stated acceptance criterion is otherwise unverifiable.
- Possibly one file under `src/Shared` (a base error type), depending on OQ-4.

**Out of scope (explicitly not doing)**

- Any implementation of `StoryGraph` in `src/Content`. Engine ships the interface; Content implements it in a later feature. The only implementation created here is a test double under `tests/`.
- YAML authoring, the YAML to JSONB compiler, `story_version`, content validation, scene text, choice labels, i18n.
- `src/Play`: sessions, event log persistence, progress, turn counters. `Transition::run()` receives `int $turn` as an argument precisely so the Engine never owns it.
- `src/Api`: controllers, DTOs, validation constraints, serialization to HTTP. Standing rule 5 means the Api must validate before calling the Engine; that validation is not written here.
- Any Doctrine entity, repository, or migration. No table, no column, no JSONB write path.
- Any use of `Rng` by any operator. A `chance` condition or a `roll` effect is explicitly deferred; `SeededRng` ships unused as a forward contract (see R10 / OQ-13).
- Any weakening of PHPStan level 8, deptrac rules or the cs-fixer config (standing rule 4), and no `phpstan-baseline.neon`.
- Rewriting `deptrac.yaml`. The Engine layer and its ruleset are already correct — see *Dependency-rule impact*.
- Scene text rendering, choice visibility vs. availability as separate concepts (a choice whose condition fails is simply unavailable), undo/rewind, branching saves.

## Data & schema impact

- **Migration needed: no.** No entity, no table, no column, no index. Standing rule 6 is not engaged.
- **Story content / JSON AST changes: yes — this feature defines the AST.** `Condition::fromArray()` and `Effect::fromArray()` fix the on-disk and JSONB representation of the 13 condition ops and 8 effect ops. Once `src/Content` compiles YAML into this shape and a `story_version` row is published immutable, the format is effectively frozen: a later change to node key names becomes a data migration over JSONB, not a code change. The plan should therefore choose the node shape deliberately (flat `{"op": "...", ...}` versus nested) and decide whether a format version marker is embedded (OQ-11).
- **`story_version` snapshot shape:** not created, but constrained. The compiled snapshot will contain scenes whose `choices[].condition`, `choices[].effects[]`, `onEnter[]` and `next` are exactly what `Condition::fromArray`, `Effect::fromArray` and the `string|list<NextRule>` union accept. The three methods on `StoryGraph` are the only read surface Content must provide.
- **Future `play_session` state column:** `GameState::toArray()` / `fromArray()` define it. Five keys (`vars`, `flags`, `inventory`, `visited`, `history`), all JSON-safe scalars and arrays. Two consequences worth stating now: (a) `history` is append-only and unbounded (OQ-9), so the row grows without limit across a long playthrough; (b) if the arrays are not canonically ordered (OQ-12), two semantically identical states serialize to different JSON, and byte-comparison or hashing of saved state becomes unreliable.
- **Floats in JSONB:** a `float` variable round-trips through `json_encode` / `json_decode` with PostgreSQL `jsonb` numeric semantics. Not a blocker here, because nothing is persisted in this feature, but `eq` on a float variable is an exact comparison and is a known correctness trap (R11).

## Dependency-rule impact

**Required edges:** `Engine -> Shared` only — and it is already present in `deptrac.yaml` as `Engine: [Shared]`. If OQ-4 resolves to "exceptions stay in Engine", this feature introduces **zero** outgoing dependencies from the Engine layer, and deptrac will report `Allowed 0` for it while still analysing real tokens.

**New or questionable edges: none. `deptrac.yaml` needs no change for this feature**, and the plan should say so explicitly, so that nobody "helpfully" grants Engine the `Framework` layer to make an import work. A proposal to edit `deptrac.yaml` during implementation should be treated as a signal that something is being imported that should not be.

Precisely what deptrac will enforce once the Engine has real classes:

- `Engine -> Engine` (intra-layer) — allowed implicitly by deptrac; no ruleset entry is needed.
- `Engine -> Shared` — allowed.
- `Engine -> Framework` (any Symfony, Doctrine, Psr, Monolog or other vendor class) — **violation**, because `Framework` is defined as "any class-like that is neither `Storyteller\*`, nor a PHP built-in, nor a dev package", and the `Engine` ruleset does not list it.
- `Engine -> Dev` (PHPUnit and the other 51 transitive require-dev packages) — **violation**.
- `Engine -> Content`, `Play`, `Api`, `Unlayered` — **violation**.
- PHP internal classes — **no entry at all**, by design. `Random\Randomizer`, `Random\Engine\Mt19937` and `Random\Engine\Xoshiro256StarStar` were explicitly probed clean during `project-skeleton`, which matters for `SeededRng`. `Random\Engine\Secure` is non-deterministic and must never be used.

**This is the first feature in which deptrac analyses a non-empty Engine layer.** The skeleton summary records the gate as vacuous in coverage while proven in mechanism (`Violations 0 / Uncovered 0 / Allowed 0`). After this feature a deptrac run should report a non-zero analysed-dependency count, which is a cheap, checkable sign that the gate stopped being vacuous — see AC-4.

Two gaps deptrac structurally cannot close, carried forward from the skeleton review and now actually relevant rather than theoretical:

1. **Vendor functions and constants are invisible to deptrac** (finding N2). `use function Symfony\Component\String\u;` inside `src/Engine` produces 0 violations, 0 uncovered and 0 warnings. `BoundedContextLayoutTest` is the only mechanism that covers that, and only for Engine and Shared. It is now load-bearing.
2. **`tests/` is outside the deptrac `paths`** (`./src` only), so the `InMemoryStoryGraph` double is unconstrained by the dependency rule. That is correct and must stay that way, but it means nothing stops a test double from drifting into shapes the real Content implementation could not produce. The double must live under `tests/` — `BoundedContextLayoutTest` would fail a `PHPUnit` import placed in `src/Engine`, and a PHPUnit-free double under `src/` would still be production code by this project's definition.

## Open questions

Fourteen questions, each with a recommended default. Accepting every default is a valid single answer at Gate A. **OQ-1, OQ-2 and OQ-5 through OQ-9 are load-bearing** — they change observable behaviour, a persisted data format, or whether a gate means anything. The rest are cheaper to revisit later.

1. **[load-bearing] Test location: `tests/Engine`, as the request says, or `tests/Unit/Engine`, as CLAUDE.md and the existing tree say?**
   *Why it matters:* this is not a style preference. `phpunit.xml` registers exactly two suites — `unit` to `tests/Unit` and `integration` to `tests/Integration`. A directory named `tests/Engine` belongs to neither, so `composer test` would never execute it: the suite would be invisible, `composer qa` would exit 0 having run zero Engine tests, and standing rule 1 would look satisfied while nothing was checked.
   *Recommended default:* **`tests/Unit/Engine/**`.** Standing rule 1 names that path literally, and `project-skeleton` decision D3 settled the identical conflict the same way.
   *Alternative:* if `tests/Engine` is genuinely wanted, a third suite must be added to `phpunit.xml` **and** standing rule 1 amended — more moving parts for no gain.

2. **[load-bearing] Coverage: add a driver, or restate the criterion?**
   *Why it matters:* the acceptance criterion "100% lines on `src/Engine`" cannot currently be produced, let alone failed. Verified facts: the Dockerfile installs `pdo_pgsql pgsql intl zip` and nothing else — **no Xdebug, no PCOV**; `composer.json` has no `coverage` script; the Makefile has no `coverage` target; `phpunit.xml` has a `<source><include>src</include></source>` block (which a driver-backed run would use) but **no `<coverage>` element**. Without a driver PHPUnit emits a notice and exits 0, so the criterion is unfalsifiable rather than failing.
   *Recommended default:* **(a) add PCOV and keep the 100% criterion.** Concretely: `pecl install pcov && docker-php-ext-enable pcov` in the dev stage — which requires `make build`, not just `make up`; a `coverage` composer script such as `vendor/bin/phpunit --testsuite=unit --coverage-text --coverage-html var/coverage`; a coverage filter scoped to `src/Engine` so `src/Kernel.php` does not dilute the figure; and `var/coverage` ignored by git. PCOV over Xdebug because it is coverage-only and much faster, and because Xdebug silently produces nothing unless `XDEBUG_MODE=coverage` is set.
   *Alternative (b):* if the image must not change, replace the criterion with a structural one — a test that enumerates the classes under `src/Engine` and asserts each has a corresponding test class — and record in the summary that line coverage is not measured, and why.
   *Rejected explicitly:* leaving it as written. That ships an acceptance criterion nobody can fail, which is worse than having none.

3. **Does this feature touch `src/Shared` at all?**
   *Why it matters:* it determines whether the Engine layer has any outgoing dependency, and therefore what the deptrac output proves.
   *Recommended default:* **no.** Keep the Engine self-contained; deptrac then reports zero outgoing dependencies for the layer, which is the cleanest possible proof of the dependency rule and matches the acceptance criterion as the user stated it.

4. **Where does `EngineException` live, and what does it extend?**
   *Why it matters:* CLAUDE.md lists "errors" among the responsibilities of `src/Shared`, while the request puts the exception family in Engine. The two readings have different deptrac consequences and different blast radii.
   *Recommended default:* **`Storyteller\Engine\Exception\EngineException`, an abstract class extending `\RuntimeException`**, with concrete subclasses in the same namespace: `UnknownVariableException`, `TypeMismatchException`, `UnknownOperatorException`, `MalformedNodeException`, `UnknownSceneException`, `ChoiceUnavailableException`, `NoNextSceneException`, `RedirectLoopException`. These errors are meaningless outside the Engine vocabulary, and because deptrac grants `Shared: []`, a Shared base could not even reference a framework exception interface.
   *Deptrac consequence of the default:* **none** — no `Engine -> Shared` edge is created and the layer has no outgoing dependency at all.
   *Deptrac consequence of the alternative* (a `Storyteller\Shared\StorytellerError` base): legal, and `Engine -> Shared` is already allowed, but it makes `Shared` non-empty and every other context inherits it. That should be a deliberate cross-context decision, not a side effect of this feature.

5. **[load-bearing] Comparison and arithmetic type rules.** Two linked sub-questions the spec leaves open.
   - **5a — are `lt` / `lte` / `gt` / `gte` legal on `string` and `bool` variables?**
     *Why it matters:* the evaluator must do something for every schema type, and whatever it does becomes authorable content. PHP string comparison is byte-wise and locale-free, so it *could* be allowed deterministically, but ordering booleans is meaningless and ordering strings invites accidental lexicographic logic that authors did not intend.
     *Recommended default:* **numeric only — `int` and `float`.** A `string` or `bool` operand throws `TypeMismatchException`. `eq` and `neq` already cover strings and bools, and allowing ordering later is purely additive.
     *Also decide when the mismatch is detected:* in general it cannot be caught in `fromArray`, because the schema need not be in hand when the AST is parsed. **Recommended default: evaluation-time**, with `fromArray` validating structure only.
   - **5b — what do `add` / `sub` do to a `string` or `bool` variable, and to an `int` variable with a float operand?**
     *Why it matters:* "concatenation" is a plausible reading of `add` on a string, and silent int-to-float promotion is the path of least resistance in PHP. Both quietly break the contract that `VariableSchema` exists to enforce.
     *Recommended default:* **`add` / `sub` are legal on `int` and `float` only; `string` and `bool` throw `TypeMismatchException` — no concatenation, no boolean arithmetic.** For mixed numerics, **the result must satisfy the declared type of the variable**: an `int` var plus `0.5` throws rather than silently becoming a float. The promote-and-round alternative is strictly worse, because rounding is hidden policy.

6. **[load-bearing] What exactly is `EffectsApplied.diff`?**
   *Why it matters:* the request names the field and nothing else, and its contents become the persisted event-log format in Play. This is a data-format decision, not an implementation detail.
   *Recommended default:* **a structural, category-keyed diff computed from before/after state**, with deterministic key ordering: `vars` as `{name: {from, to}}`; `flags` as `{added: list, removed: list}`; `inventory` as `{key: {from, to}}`, where a removed key has `to: 0`; `visited` as `{scene: {from, to}}`. A log reader wants to know what changed, not what was attempted, and a diff survives effect reordering. Cost: O(size of state) per transition unless computed incrementally — acceptable at MVP scale, and stated so nobody is surprised later.
   *Alternative:* the ordered list of applied `Effect` nodes — cheaper and more faithful to authorial intent, but it duplicates story content into the log and says nothing about outcomes, for example a `remove_item` that was clamped at 0.
   *Also decide:* is `EffectsApplied` emitted when the diff is empty, and is it emitted once per phase (choice effects, then `onEnter`) or once per transition? **Recommended default: once per phase, skipped when the diff is empty.**

7. **[load-bearing] Does `goto` short-circuit the remaining effects in its list?**
   *Why it matters:* it changes which effects are applied in a very common authoring pattern, and the request does not say.
   *Recommended default:* **yes — the first `goto` in a list stops processing, and effects after it are not applied.** That is redirect semantics, it is what an author expects from a jump, and it makes the outcome independent of how many `goto` nodes a list happens to contain.
   *Alternative:* "last goto wins, all effects apply" is defensible, but it makes apparently-unreachable effects reachable.
   *Either way a test must pin it*, including a list that contains two `goto` nodes.

8. **[load-bearing] What does the redirect counter of 5 count, and does the "`onEnter` goto allowed once more" clause survive?**
   *Why it matters:* the request contains both a limit of 1 ("allowed once more") and a limit of 5 ("throw after 5 redirects"), and does not say whether the choice-effect `goto` counts. An off-by-one is either a spurious exception on a legitimate chain or an unbounded loop.
   *Recommended default:* **one counter per `Transition::run()` call, incremented on every `goto` that actually redirects — the choice-effect `goto` included — throwing `RedirectLoopException` when the sixth redirect is attempted.** The "allowed once more" phrasing is dropped as superseded: there is one limit, 5, not a limit of 1 with a guard of 5 behind it. A single counter is the only version that cannot be reasoned about two ways.
   *Alternative:* a visited-scene set with true cycle detection, which catches A to B to A immediately but forbids legitimate re-entry. Choose it only if cycles should be rejected rather than merely bounded.
   *Tests must cover exactly 5 redirects (passes) and 6 (throws).*

9. **[load-bearing] Is `history` append-only and unbounded, and does `visited` count the scene currently being entered?**
   *Why it matters:* (a) decides whether a long playthrough grows a JSONB row without limit; (b) decides whether an author can ask "have I been here before?" inside a scene's own `onEnter`; (c) decides whether the opening scene is ever counted.
   *Recommended defaults:* **(a) `history` is append-only and unbounded inside the Engine.** Capping or windowing belongs to Play at the persistence boundary; the Engine must not silently drop data. **(b) `visited` is incremented *after* `onEnter` effects run**, exactly as the step order in the request states — which means `visited(sceneX, 1)` evaluated inside the `onEnter` of scene X is **false on the first entry**. That is surprising but defensible, and it must be documented and tested, because the alternative (increment before `onEnter`) makes "have I been here before?" unanswerable inside `onEnter`. **(c) the starting scene is not marked visited by `GameState::initial()`** — nothing entered it; if a story should count its opening scene, Play marks it explicitly.
   *Please confirm (b) and (c) specifically:* they are cheap to change now and a content-wide bug later.

10. **Must `Transition` verify that the resolved next scene exists?**
    *Why it matters:* a dangling `goto` is the single most likely content bug, and the Engine is the last place that can catch it cheaply.
    *Recommended default:* **yes.** `Transition::run()` throws `UnknownSceneException` if `currentScene` is unknown to the graph, or if the resolved target fails `hasScene()`. `NextSceneResolver` has no graph and therefore validates nothing beyond "a rule matched". Standing rule 5 says the Engine trusts its inputs, but `StoryGraph` is an interface implemented by another bounded context, not external user input.

11. **Does the serialized `GameState` carry a format version?**
    *Why it matters:* the array form becomes a JSONB column in Play. Without a version marker, a future format change is a guess rather than a migration.
    *Recommended default:* **yes — a `v` key with value `1`**, and `fromArray()` rejects an unknown version with `MalformedNodeException`. It costs one key.
    *Alternative:* say no if a minimal JSONB payload matters more than forward migration safety.

12. **Canonical ordering of `vars`, `inventory`, `visited` and `flags`.**
    *Why it matters:* this is what makes the determinism criterion meaningful. PHPUnit compares arrays by key order for `assertSame` and by content for `assertEquals`, and `json_encode` is order-sensitive either way. Without a rule, the determinism test is either vacuous or flaky, and any future hashing of saved state is unreliable.
    *Recommended default:* **key-sorted on construction** for `vars`, `inventory` and `visited`; **sorted and de-duplicated** for `flags`, which is a set represented as a `list<string>`; **insertion order preserved** for `history`, which is a sequence, not a set.

13. **Does `Rng` / `SeededRng` ship now, unused?**
    *Why it matters:* nothing calls it, yet a 100%-coverage bar forces tests for it, and a reviewer may reasonably call it YAGNI.
    *Recommended default:* **yes, ship it**, with a docblock stating that it is a deliberate forward contract for a future `chance` / `roll` operator, and that `Transition` already threads `int $turn` for exactly this reason. Its tests must assert the determinism *property* — same seed and same turn give an identical sequence, a different turn gives a different one — and never golden numbers from one particular PHP build. If `Random\Randomizer` is used, note that it is a PHP built-in and therefore invisible to deptrac, which is permitted; `Random\Engine\Secure` must never be used.
    *Alternative:* defer it to the feature that needs it, trading a small YAGNI debt for one fewer unused class.

14. **Is a written AST spec a deliverable of this feature?**
    *Why it matters:* the CLAUDE.md rule for adding an operator names "the AST spec" as one of three places to update, and that document does not exist. After this feature it either exists or the rule points at nothing.
    *Recommended default:* **yes — a short `docs/engine/ast.md`** listing every condition and effect op with its array shape, required keys, defaults and error cases. This is also what `src/Content` will be written against.
    *Alternative:* declare the docblocks on the two enums to be the spec, and record that in `00-summary.md` — acceptable, but it must be said out loud rather than left implicit.

**Not put to the user**, because they can be decided here with a stated assumption: the PHP version features relied on, the location of `InMemoryStoryGraph`, and the fact that `deptrac.yaml` needs no change. See *Assumptions made*.

## Acceptance criteria

Every criterion is checkable by a command or by reading a named file. AC-1 to AC-6 are the quality gates; AC-7 to AC-12 are structural; AC-13 to AC-20 are behavioural; AC-21 is coverage and is conditional on OQ-2.

1. `make up` succeeds and **`make qa` exits 0 inside the container**, with its output showing all four sub-checks running in order — `php-cs-fixer --dry-run`, `phpstan`, `deptrac`, `phpunit` — and `qa` failing if any one of them fails (no `|| true`, no swallowed exit code).
2. `composer cs-check` exits 0: every new file under `src/Engine/**` and `tests/Unit/Engine/**` begins with `declare(strict_types=1);` and conforms to `@PSR12` plus the project rules `ordered_imports` (alpha), `single_quote`, `trailing_comma_in_multiline` and `no_unused_imports`. Deliberately removing the strict-types line from one new file makes this criterion fail.
3. `composer phpstan` exits 0 at **level 8** with `phpVersion: 80500`, over both `src` and `tests`, with **no** `phpstan-baseline.neon` added and **no** new `@phpstan-ignore`, `@phpstan-ignore-next-line` or equivalent suppression anywhere in the diff.
4. `composer deptrac` exits 0 with **0 violations and 0 uncovered**, and — unlike every previous run — reports a **non-zero** count of analysed dependencies now that the Engine layer is populated. (`project-skeleton` left it at `Allowed 0` on an empty tree.)
5. `composer test` exits 0 with **0 failures, 0 errors, 0 skipped, 0 risky and 0 warnings**, which `phpunit.xml` enforces through `failOnRisky`, `failOnWarning` and `failOnSkipped`.
6. **`deptrac.yaml` is unchanged by this feature** — verifiable with `git diff --stat` — and its ruleset still reads exactly `Engine: [Shared]`.
7. Every new production file lives under `src/Engine/**`. `git diff --name-only` shows no new file under `src/Content`, `src/Play` or `src/Api`, and none under `src/Shared` unless OQ-4 was answered otherwise.
8. No file under `src/Engine/**` contains `use`, `use function` or `use const` for `Symfony`, `Doctrine`, `Psr`, `Monolog` or `PHPUnit`, and `tests/Unit/Shared/BoundedContextLayoutTest.php` passes **without modification**.
9. No file under `src/Engine/**` calls `rand`, `mt_rand`, `random_int`, `shuffle`, `time`, `microtime`, `date` or `uniqid`, reads a superglobal, or declares a static mutable property. Checkable with `rg` over `src/Engine`.
10. The `InMemoryStoryGraph` test double lives under `tests/`, not under `src/`, and no production class implements `StoryGraph`.
11. Every Engine test lives under `tests/Unit/Engine/**` and is executed by `vendor/bin/phpunit --testsuite=unit` (OQ-1); that suite exits 0 on its own, and its reported test count is substantially higher than the 24 tests the skeleton left behind — so an unregistered suite cannot hide behind a green exit code.
12. `ConditionOp` and `EffectOp` are backed enums whose cases are exactly the 13 condition ops (`eq`, `neq`, `lt`, `lte`, `gt`, `gte`, `flag`, `not_flag`, `has_item`, `visited`, `and`, `or`, `not`) and the 8 effect ops (`set`, `add`, `sub`, `set_flag`, `clear_flag`, `give_item`, `remove_item`, `goto`), with a test asserting the full case list so that a silently added, removed or renamed operator fails the suite.
13. **Determinism.** One test runs the *same* `Transition::run(...)` inputs twice and asserts the two `TransitionResult` values are equal, event list included. A second test reaches the same state through two *different* effect orderings and asserts that the resulting `GameState` and its `toArray()` output are equal — which is what the canonical ordering chosen in OQ-12 makes true.
14. **Round-trip.** `GameState::fromArray($state->toArray())` equals `$state` for a state exercising all five fields, for an empty state produced by `GameState::initial()`, and for a state containing a `float` variable.
15. **Every operator has a test.** For each of the 21 ops there is at least one satisfied and one unsatisfied case; `and`, `or` and `not` are covered with nested children; `has_item` and `visited` are covered below, at and above their thresholds, including the default of 1; and a variable absent from the state is covered and resolves to the **schema default**, never to `null`.
16. **Every exception has its own test case:** unknown variable, type mismatch in both the OQ-5a and OQ-5b forms, unknown condition op, unknown effect op, malformed node (a required key missing), unavailable choice, unknown scene, no matching `next` rule, and redirect loop.
17. **`NextSceneResolver`.** A plain `string` resolves to itself; an ordered rule list returns the **first** match even when a later rule would also match; a rule without `if` acts as the fallback and is used only when no earlier rule matched; and a list with no match and no fallback throws `NoNextSceneException`.
18. **`EffectApplier`.** `remove_item` never drives a quantity below 0 and removes the key entirely at exactly 0; `give_item` and `remove_item` default to a quantity of 1; `goto` sets `EffectResult::$redirectTo` and **does not mutate** the state; and the short-circuit behaviour chosen in OQ-7 is asserted on a list containing an effect after the `goto`.
19. **`Transition`.** Covered: the happy path in order — choice effects, next resolution, target `onEnter`, visited and history update, events; a choice whose condition is false throws `ChoiceUnavailableException`; a choice key absent from the scene throws; a `goto` in the choice effects overrides the declared `next`; an `onEnter` `goto` redirects again; the redirect counter passes at the OQ-8 limit and throws at limit+1; `isEnding` is true exactly when `StoryGraph::isEnding()` says so; and the emitted events are `ChoiceMade`, `EffectsApplied`, `SceneEntered` and — only for an ending — `EndingReached`, in a deterministic order the test asserts explicitly.
20. **Immutability.** For every value object under `src/Engine`, a test asserts that each `with*` method returns a **new** instance (`assertNotSame`) and leaves the receiver unchanged (a field assertion on the original).
21. **Coverage, conditional on OQ-2a.** `composer coverage` (or `make coverage`) runs with a working driver and reports **100.00% of lines** for `src/Engine`, with the report scoped to `src/Engine` so that no other directory dilutes the figure. If OQ-2b is chosen instead, this criterion is replaced by: a test enumerates the classes under `src/Engine` and asserts that each has a corresponding test class under `tests/Unit/Engine`, and `00-summary.md` records that line coverage is **not** measured and why.

## Assumptions made

- **Platform, verified rather than assumed.** `composer.json` requires `"php": ">=8.5"` with `config.platform.php` pinned to `8.5.0`; the Dockerfile is `php:8.5.12-fpm`; `phpstan.neon` sets `phpVersion: 80500`; php-cs-fixer 3.95 declares `PHP_VERSION_SYNTAX_SUPPORTED = '8.5'`. So `readonly class` (8.2), backed enums (8.1), readonly promoted constructor properties, `never`, first-class callable syntax, readonly reinitialization inside `__clone()` (8.3) and `#[\Override]` (8.3) are all available. **The assumption the plan should adopt is to use no PHP-8.5-exclusive syntax** — no pipe operator, no `#[\NoDiscard]`, no attributes on constants. Nothing in this feature needs it, and brand-new syntax is where php-cs-fixer and PHPStan support is thinnest; a gratuitous dependency on it risks a gate failure that standing rule 4 forbids working around.
- **The quality bar is four commands.** `composer qa` is defined in `composer.json` as `cs-check`, `phpstan`, `deptrac`, `test`, in that order; `make qa` is `docker compose exec -T php composer qa`. **The `php` container must already be running** — `guard-running` exits 1 with `php container is not running - run 'make up' first` — and `make up` also starts Postgres, because the `php` service declares `depends_on: postgres: condition: service_healthy`. If OQ-2a is accepted, `make build` is required before `make up`. The Engine unit tests themselves need no database.
- **`deptrac.yaml` needs no change.** The `Engine` layer and the `Engine: [Shared]` ruleset already exist and are correct for this feature.
- **`InMemoryStoryGraph` lives under `tests/Unit/Engine/`** (optionally in a `Double/` subdirectory), never under `src/`. `tests/` is outside the deptrac `paths`, so it is unconstrained by the dependency rule, and `BoundedContextLayoutTest` would fail a `PHPUnit` import placed in `src/Engine`.
- **Subdirectories under `src/Engine/` are permitted.** The deptrac collector is `src/Engine/.*`, and `BoundedContextLayoutTest::CONTEXT_DIRECTORIES` only asserts that `src/Engine` itself exists. A new top-level directory under `src/` — for example `src/Ast` — would land in the `Unlayered` layer, be granted nothing, and fail loudly, so all Engine code stays inside `src/Engine/**`.
- **Test namespaces are `Storyteller\Tests\Unit\Engine\*`**, under the existing `Storyteller\Tests\` to `tests/` PSR-4 map. No `composer.json` autoload change is needed.
- **`requireCoverageMetadata="false"`** means `#[CoversClass]` attributes are optional today. If OQ-2a is accepted, adding them is still worthwhile for an accurate per-class report, but flipping `requireCoverageMetadata` to `true` is a separate decision with repository-wide consequences and is **not** assumed here.
- **"Pure" is read as:** no I/O, no globals, no static mutable state, no clock, no randomness source other than an injected `Rng`, and no vendor class. PHP built-ins — `RuntimeException`, `JsonException`, `Random\*` — are permitted and are invisible to deptrac by design.
- **`int $turn` on `Transition::run()` is the caller's turn counter** (Play's). The Engine never derives it and never increments it. The four event classes carry no timestamp for the same reason: Play adds time when it logs.
- **"Green" means green locally in the container**; no CI provider is configured. Following the `project-skeleton` precedent, gate results should be verified inside the container rather than reported from a host run.
- **One environmental caveat.** `docker compose ps` was blocked by the permission system during this analysis, so the running state of the stack is unverified. Everything stated about the container, its extensions and the gate commands is read from `Dockerfile`, `compose.yaml`, `Makefile` and `composer.json`, which is sufficient for every conclusion drawn here — in particular for R1, which rests on the extension list in the Dockerfile.
